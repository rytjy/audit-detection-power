## 3. COVERAGE.md 格式（收尾脚本会自己重算）

```markdown
TOTAL: 5723

COVERED:
- src/machine/Machine.sol
- src/bridge/BridgeController.sol
- ...

UNREAD:
- src/caliber/CaliberMailbox.sol (原因: 时间盒到点)
- makina-periphery  (原因: 独立 repo，未 stage；代价: 真实残余风险)
```

- `TOTAL:` = 声明的 in-scope SLOC 总量（自己从 scope 表重推，别抄快照）
- `COVERED:` 下的路径**必须真实存在** —— `box_closeout_check.sh` 会 `find` 验证并**自己重算 SLOC**
- `UNREAD:` 每行**必须带原因**，否则收尾 FAIL（弃读必须带代价）

🔴 **A1 政策（全量覆盖做不到 → 不靠自觉，靠标签）**：`TOTAL > 5,000` 的靶**本来就做不到全读**。所以：
- 结论**必须**带标签：`覆盖: X/Y SLOC (Z%) — 部分覆盖`（`box_closeout_check.sh` 会强打这个标签）
- `Z < 30%` ⇒ **不足以支撑任何结论**（脚本直接 FAIL）
- 想声称"全量" ⇒ 必须 `Z = 100%`，没得商量

## 3.5 判据清单（源自 2026-09-27 真实漏点 —— 读到就必须问）

> **来源**：C4 `2025-07-lido-finance` 自我基准。我们**逐行读过那两个函数、还写了 negative**，
> 却把真问题**判成了非问题**。两条都**不需要领域知识、不需要链上数据** ⇒ **纯判据缺失，必须进清单**
> （基准产物：`bench/BENCHMARK_lido-2025-07.md` · 盲测清单 `bench/BLIND_LIST_lido-2025-07.md`）。
>
> **2026-10-01 增补 3–7（来自盲测 #3 `2025-10-sequence`）**：那场 **H+M=6、覆盖 100%、召回仅 1/6、假阳性 5/6**，且**漏掉的 5 条里有 4 条是「读到但没连接」**
> ⇒ 全是判据缺口，不需要新领域知识。产物：`bench/BENCHMARK_sequence-2025-10.md`。
>
> **2026-10-01 晚 增补 8–12（来自盲测 #4 `2025-11-megapot`）**：那场 **H+M=11（3H+8M）、覆盖 100%、严格命中仅 1/11 = 9.1%**，
> 且 **3 条 High 全部落在我们「读过并主动否定」的代码区**（`_bridgeFunds` 邻域 / 组合计数 gas / LP 池上限）。
> ⇒ **这是四次基准里最低的一次**，产物：`bench/BENCHMARK_megapot-2025-11.md`。

1. **批量操作的部分失败** —— 循环处理多条输入时，**单条无效**是否导致**整批回滚**？
   ⇒ 问：一条坏条目能否让全部合法条目一起失败（可用性/DoS 面）？
   ⇒ 实例：`CSStrikes.processBadPerformanceProof`（官方 **L-01** Batch Operation Fully Reverts on Invalid Ejection Entry）
2. **跨函数状态生命周期耦合** —— 一个函数改了状态（root / 周期 / 计数），**是否让另一个函数先前产生的凭据静默失效**？
   ⇒ 问：状态变更后，之前"有效"的 proof / 签名 / 授权会不会**无声作废**？
   ⇒ 实例：赛季中更新 Merkle root 作废旧 proof（官方 **L-02** Mid-Season Merkle Root Update Invalidates Previously Valid Proofs）

3. **规范符合性 / 集成破坏** —— 代码「能跑、也无利可图」，但**违反它声明要兼容的标准**（ERC-4337 / ERC-4626 / EIP-712…），会不会破坏集成方的预期流程？
   ⇒ 问：**别只用「攻击者能否获利」当筛选轴** —— 打包器 / 网关 / 集成方的**预期行为被破坏**本身就是可报问题（DoS · 兼容性 · UX）。
   ⇒ 实例：`Factory.deploy` 在账户已存在时 revert，而 ERC-4337 要求**返回地址**（#3 官方 **M-04**）——我们当时**看过这个函数却主动否定**，因为只问了「攻击者能否抢占」。
4. **接口契约一致性**（实现 vs `interface` / natspec 明文） —— 实现返回值与语义，是否与接口的**书面承诺**一致？
   ⇒ 问：文档说「返回 X」，实现是否**返回常量/别的东西**？下游是否把这个返回值当真实数据用？
   ⇒ 实例：`BaseAuth.recoverSapientSignature` 无条件返回 `bytes32(uint256(1))`，而 `ISapient` 要求返回 signer 的 imageHash（#3 官方 **M-03**）。
5. **外部 self-call 会改变 `msg.sender`** —— 经 `this.f()` 的外部自调用路径里，`msg.sender` 变成**合约自身**，不是原始调用者。
   ⇒ 问：该路径上有没有**基于 `msg.sender` 的绑定 / 白名单 / 权限判断**？它比的是不是**错的那个地址**？
   ⇒ 实例：`ERC4337v07.validateUserOp` → `this.isValidSignature(...)` ⇒ 静态签名的 caller 绑定拿钱包地址去比 EntryPoint ⇒ revert / DoS（#3 官方 **M-02**）。
6. **签名/授权标志位要逐位穷举** —— flag / 位域**每一位都要问「置 0 / 置 1 各关掉什么校验」**。
   ⇒ 问：默认（位=0）时**哪些校验被跳过**？被跳过的段落里有没有安全关键量（地址、快照、根哈希）？
   ⇒ 实例：`BaseSig.recover` 的 **bit6(`0x40`)** 未置位 ⇒ checkpointer 校验块被整段跳过 ⇒ `_checkpointer` / `snapshot` 全留零值（#3 官方 **H-01**）。同型：**bit1(`noChainId`)** 决定链上重放域。
7. **「先消费后校验」的顺序组合** —— 状态消费（nonce / 序号 / 额度）**发生在签名校验之前**时，失败路径是**回滚消费**还是**留下已消费**？
   ⇒ 问：整批回滚后**签名是否仍然有效**（nonce 未消费）⇒ 能否**部分重放 / 抢跑**（尤其中继者可见 mempool 时）？
   ⇒ 实例：`Calls.execute` 先 `_consumeNonce` 再 `signatureValidation`，配 `BEHAVIOR_REVERT_ON_ERROR` 整批回滚 ⇒ 失败的多调用签名仍可被**拆成子集**执行（#3 官方 **H-02**）。

8. **外部调用的 target / calldata 是否用户可控** —— 顺着**任何**带外部调用的 claim / withdraw / refund / bridge 路径**再往下读一层**：callee 与 data 是谁给的？
   ⇒ 问：攻击者能否把 target 设成任意合约、把 data 设成任意 selector？被调用方会不会用**受害者已授权**的额度？
   ⇒ 实例：`JackpotBridgeManager._bridgeFunds` 对用户可控的 `_bridgeDetails.to/.data` 发任意调用 ⇒ 用 `safeTransferFrom` 偷走桥托管的 NFT（#4 官方 **H-01**）。⚠️ **我们读过它的入口（`claimWinnings:225-243`）却没往下读一层。**
9. **复杂度 / gas 上界** —— 对「**循环 × 组合计数 × 内部数组**」的结算 / 清算 / 领取路径，**除正确性外必须问代价**。
   ⇒ 问：最坏输入下 gas 是否超链上 tx gas limit？谁付这个代价、会不会把**整个结算**卡死？
   ⇒ 实例：`TicketComboTracker.countTierMatchesWithBonusball` 子集匹配未优化 ⇒ 超 Base 链 tx gas limit、抽奖无法结算（#4 官方 **H-02**）。⚠️ **我们逐行读完并判定「数学精确、无重复计数」—— 只核了正确性，没核代价。**
10. **上限 / 不变式在每条路径是否都复用** —— 凡有 `XxxCap` / `maxXxx` / 不变量，**枚举每一条会改变被约束量的路径**，逐条问「这条走了 cap 吗？」
    ⇒ 问：新函数 / 新分支 / 新结算路径是否**绕过了**既有上限检查？
    ⇒ 实例：`JackpotLPManager.processDrawingSettlement` 的 `newLPValue` **不复用 `_calculateLpPoolCap`** ⇒ 结算后 LP 池可超上限（#4 官方 **H-03**）。⚠️ **我们读过该函数，结论「deposit-at-NAV 自洽」—— 核了份额会计，没核上限不变式。**
11. **活跃期内可变全局配置清单** —— 把「**期初快照 vs 结算时读全局**」做成一张**对读表**：列出活跃期内所有可变全局量（费率 / 价格 / 计算器 / provider / 管理员），逐个问「改它会让结算读到什么」。
    ⇒ 实例：#4 官方 **M-01 / M-02 / M-07 / M-08 四条全是这个模式**（期中改 `protocolFee`/`referralFee`/`payoutCalculator`/`entropy`）。⚠️ **我们只点到 `ticketPrice`、`referralFee` 两个实例，没把它当模式系统扫。**
12. **治理路径自身的 DoS 面** —— 参数设置函数里形如「**新值必须 ≥ 当前值**」的校验 = **可被外部操作阻断**。
    ⇒ 问：能否通过改变被比较量（存钱、增发、堆 pending）让治理函数**永远 revert**？
    ⇒ 实例：`setLPPoolCap` 要求新上限 ≥ 当前池 + 待入金 ⇒ LP 猛存钱即阻断 `setNormalBallMax`/`setGovernancePoolCap`/`setLpEdgeTarget`/`setReserveRatio` 全部更新（#4 官方 **M-03**）。

> **用法**：读到任何「循环 + 校验」「状态更新 + 前置凭据」「外部自调用」「签名标志位」「先消费后校验」「外部调用」「上限 / 不变量」「治理 setters」的函数，**逐条过一遍**，
> 并把结论写进 candidates（成立 / 不成立 + 依据）。**这十二条是我们用真实代价换来的**（#1 两条 · #3 五条 · #4 五条）。
>
> 🔴 **#4 的教训（必读）**：那场 **H+M=11、覆盖 100%、严格命中仅 1/11**，而且 **3 条 High 全部落在我们「读过并主动否定」的代码区**。
> ⇒ **「我读过了」不等于「我验过了」**：读完一遍只证明覆盖，不证明没漏。重点是 **8 / 9 / 10 三条**——它们治的不是「没读到」，而是「读到了但只核了一个维度（正确性）就放过」。

### Step 3.6 反向闸门 —— **报之前必过**（2026-10-01 立 · 来自盲测 #3 的 83% 假阳性）

> **依据**：两场盲测**同向** —— hybra **9/12** 假阳性 · sequence **5/6**（命中仅 1/6）。
> **诊断**：我们的假阳性**不是编造**（引用行都经父线程回读成立），而是**「把观察当问题」**。
> ⇒ §3.5 管「**该问什么**」（扩大可报面）；本节管「**什么不算**」（收窄筛选轴）。**两个都过，才准写进报告。**

**五问（任一答不上来 ⇒ 降为 code smell，不进报告）**

1. **谁受损？** 能指名**具体受害者**与**具体损失**吗？
   ⇒ 说不出「谁来受、受什么损」⇒ 行为怪异，但不是漏洞。
   ⇒ 反例：`Hooks.fallback` 对未知 selector 返回成功（我们 C-06）—— **要有人真的据此误判**才算影响，说不清 ⇒ 不报。
2. **前提可达吗？** 触发是否需要**不可能状态 / 攻击者自伤 / 未文档化的外部条件**？
   ⇒ 反例：`incrementUsageLimit` 无门禁（C-04）—— 但它**只能写调用者自己的表项**，跨账户影响构造不出来 ⇒ 不报。
3. **是「不符预期」还是「设计选择」？** 项目方能否一句话回「这是我们想要的」？
   ⇒ 能 ⇒ code smell。
   ⇒ 反例：`behaviorOnError==3` 走成功分支（C-05）—— 想报必须**先证明签名者能构造出 3 且有受害者**。
4. **攻击者得到什么？（⚠️ **按平台口径** —— 先看下方「平台开关」）** 无收益 ⇒ **赏金平台**不付（Immunefi 明文 `no profit motive` 行不付获利型攻击）；**竞赛不一定**。
5. **是否已被覆盖？** 前序审计 / V12 清单 / 上游同代码 / 平台禁止行为族（`L-DoS`）。
   ⇒ 被覆盖 ⇒ 不报（这是我们十场里最常见的否决）。

**两条降级口诀**
- 需要「**如果……就好了**」才能成立 ⇒ code smell
- 只能写成「**建议加固 / 建议重构**」⇒ code smell（除非该平台收 QA 且你确定本场计分）

**与量级轴的关系**：过了本节再谈档位；量级不足（dust · `>1%` 阈值行 · `in excess of gas costs`）⇒ 即使成立也**不可付**（见 `PAYABLE_ROWS_SCAN.md` / `impact_gate.py`）。

### Step 3.9 薄分叉闸门（机械 · 2026-09-29 立 · 来自 Aborean 那轮的真实失败）

选靶后、开盒前**必须**跑一次（判定用机械证据，不靠感觉）：

```bash
# 目标仓 vs 其上游/声称的 fork 源
find <target>/contracts -name '*.sol' | while read f; do
  p=${f#<target>/}; u=<upstream>/$p; [ -f "$u" ] || continue
  # 归一化重命名（把本项目的名字换成上游的名字）后再比
  diff -q <(sed -e 's/<Project>/<Upstream>/g' "$f") "$u" >/dev/null || echo "DIFF $p"
done
```

**判定：归一化后「实质差异行数 < ~200 行」⇒ 判为薄分叉 ⇒ 选靶阶段否决。**

**理由（实证）**：`Aborean Finance`（Abstract 链 · TVL $3.84M）是 **Aerodrome 的重命名分叉**，净功能改动仅 **~130 行**（集中在 `PoolFactory` / `Router`），读全后自洽无洞；且两处"可疑缺检查"（`Voter.poke` 无授权、`Voter.depositManaged` 无 `_reset`）与上游**逐字相同** ⇒ 报出去等于**重复上游已审覆盖面**。

> **薄分叉为什么必须否决**：① 上游代码**已被审过、被无数人读过**（违反 Doctrine：只打 AI/审计没覆盖的码）② 我们的增量价值只在**改动面**，改动面太小 ⇒ **期望发现数 ≈ 0**
